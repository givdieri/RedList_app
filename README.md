# RedList_app

## Modular Shiny application for fungal Red List assessment in Flanders

This repository contains the redevelopment of the Flemish fungal Red List workflow into a transparent, modular, expert-reviewable Shiny application.

The project is based on the historical FUNBEL Red List workflow and the later combined FUNBEL + waarnemingen.be workflow, with methodological inspiration from the butterfly Red List framework of Dirk Maes and the original Czech fungal Red List Shiny application.

The goal is not full automation of Red List decisions.

The goal is a reproducible decision-support system where:

* calculations are transparent
* thresholds are user-settable
* legacy Criterion A results are reproducible
* Criterion B is rebuilt more transparently
* expert interpretation remains central

Final Red List categories are always expert-reviewed.

---

# Project principles

## Primary backend

The main analytical backend is:

## combined FUNBEL + waarnemingen.be dataset

represented by:

```text id="f15s1v"
data_raw/Data_updated.xlsx
```

with Flemish spatial restriction applied through IFBL reference tables.

This replaces older separate FUNBEL-only and Natuurpunt-only workflows.

---

## Preprocessing is separate

Raw data cleaning is performed once by the project owner using standalone scripts.

App users never work with raw source files.

They interact only with cleaned app inputs generated by preprocessing.

This ensures:

* reproducibility
* transparent exclusions
* stable analytical inputs
* expert confidence

---

## Legacy compatibility

The first implementation must reproduce the old Criterion A workflow as closely as possible.

This is the primary validation target.

Criterion B is intentionally rebuilt more transparently and is not expected to exactly reproduce older scripts.

---

## Expert-reviewed final category

The app calculates:

* Criterion A outputs
* Criterion B outputs
* supporting diagnostics
* maps
* raw record inspection

but the final Red List category remains:

## an expert-reviewed decision

not a fully automated classification.

# Default analytical assumptions

## Spatial unit

Default:

## uurhok / ifbluurhok = 2 × 2 km

This is the operational analytical unit for v1.

---

## Historical vs current split

Default:

```r id="3f9svd"
historical <= 2000
current >= 2001
```

but this must be user-settable.

---

## DD default rule

Default:

## occupied IFBL grids < 5 in both periods

but this threshold must also be user-settable.

---

## Validation

In v1:

* retain all records
* preserve raw `validatie` field exactly as-is
* do not automatically exclude records by validation class

The field must remain visible to users.

Future versions may allow stricter filtering.

# Important implementation rule

## Do not silently change Red List logic

Any methodological deviation from the legacy workflow must be:

* explicit
* documented
* justified

especially for:

* Criterion A
* DD handling
* fragmentation rules
* decline estimation
* final category assignment

Transparency is more important than convenience.

---

# First implementation target

The first production milestone is:

## preprocessing + Criterion A + species review workflow

not full automation of all criteria.

This provides the strongest scientific foundation for later expansion.
